## 2. STAR 面试讲解稿

### Situation（背景）

"在日常工作和学习中，我经常需要处理大量视频文件 — 课程录制、会议回放、素材归档。这些视频往往体积过大，上传到网盘、发送给同事、或者存储到移动硬盘时都会遇到问题。"

"我调研了市面上的工具，发现存在明显的断层：在线工具有文件大小限制和隐私风险；HandBrake 功能强大但界面复杂，普通用户难以理解 CRF、preset 等概念；FFmpeg 命令行最灵活但门槛最高。"

"我想要的其实很简单：选一堆视频，点一下，告诉我大概要多久，压缩完告诉我节省了多少空间。但现有工具都没有很好地满足这个需求。"

### Task（任务）

"我决定自己做一个桌面端的批量视频压缩工具，目标是：

1. **零门槛** — 用户不需要知道什么是 FFmpeg
2. **批量优先** — 单文件压缩是特殊情况，批量才是常态
3. **可控可解释** — 告诉用户压缩要多久、为什么这么慢、结果如何
4. **数据安全** — 绝不能因为压缩操作丢失原始文件"

### Action（行动）

"我选择了 Electron + React + TypeScript 技术栈，因为 Web 技术开发效率高，React 生态丰富，后续也容易扩展到其他平台。"

"在产品设计上，我做了几个关键决策：

1. **6 种压缩模式** — 从简单的'平衡'、'质量优先'到精确的'Target Size Accurate（two-pass）'，覆盖不同用户场景。用户最常见的需求是'压缩到 100MB 以内'，所以 Target Size 是核心功能。

2. **三层 ETA 预估** — 规则估算（基于像素复杂度）→ 历史 benchmark（基于之前的压缩记录）→ Quick Probe（压缩 5 秒片段实测）。越用越准，让用户不再焦虑等待。

3. **backup-then-swap** — 替换原文件时，先压缩到临时文件，验证完整性后备份原文件，替换成功后删除备份，失败则自动回滚。这个设计确保了零数据丢失。

4. **内嵌 FFmpeg** — 用户不需要手动安装 FFmpeg，应用内嵌二进制文件，还支持应用内更新。"

"在技术实现上，我设计了清晰的三进程架构：

- **Main Process** — 13 个后端模块，处理文件扫描、视频分析、压缩执行、队列管理等
- **Preload Bridge** — 通过 contextBridge 暴露受控 API，不开启 nodeIntegration
- **Renderer** — React SPA，Zustand 状态管理，三层状态守卫防止数据不一致

我还建立了完整的测试体系，138 个测试用例覆盖所有核心模块。"

### Result（结果）

"最终成果：

1. **功能完整** — 批量压缩、6 种模式、ETA 预估、历史记录、FFmpeg 管理，所有核心功能都已实现
2. **质量达标** — TypeScript 类型检查通过、构建通过、138 个测试全部通过、Lint 零错误、打包通过
3. **可分发** — 可以一键生成 Windows NSIS 安装包，用户下载安装即可使用
4. **作品集价值** — 展示了从需求分析、产品设计到工程落地的完整能力"

## 3. 面试官可能追问的问题和回答

### Q1：你为什么做这个项目？

**回答：**

"两个原因。第一是真实需求 — 我自己就是目标用户，经常需要批量压缩视频，但现有工具都不太好用。第二是能力展示 — 我想证明 AI 产品经理不只是写 PRD，还能从 0 到 1 做出一个可运行的产品。"

"这个项目让我完整走了一遍产品开发流程：用户调研、需求分析、技术选型、架构设计、编码实现、测试验证、打包分发。这种全链路的经验对产品经理来说非常宝贵。"

---

### Q2：和普通视频压缩软件有什么不同？

**回答：**

"最大的不同是**批量工作流**的设计。大多数压缩工具是'单文件'思维 — 选一个文件，调参数，压缩。ShrinkFlow 是'批量'思维 — 拖拽整个文件夹，自动扫描、去重、排队、追踪结果。"

"第二个不同是**数据安全**。很多工具直接覆盖原文件，一旦出问题就丢数据。ShrinkFlow 的 backup-then-swap 策略确保了零数据丢失。"

"第三个不同是**可解释性**。三层 ETA 预估系统让用户知道要等多久，压缩结果的详细展示让用户知道节省了多少空间。用户不是在'黑盒'里等待。"

---

### Q3：你如何设计压缩模式？

**回答：**

"我从用户场景出发，而不是从技术参数出发。用户不关心什么是 CRF、什么是 preset，他们关心的是：

- 我想压缩视频，但不想损失太多质量 → **Balanced**
- 质量最重要，文件大小无所谓 → **Quality First**
- 我就想最小体积，质量可以牺牲 → **Smallest Size**
- 我想压缩到 100MB 以内 → **Target Size Fast/Accurate**
- 我不确定选什么，给我一个最安全的 → **Default（兼容高质量）**"

"每种模式背后是不同的 FFmpeg 参数组合，但用户只需要理解'场景'，不需要理解'参数'。"

---

### Q4：Target Size Fast 和 Accurate 有什么区别？

**回答：**

"核心区别是**编码次数**和**精度**。"

"**Fast** 是单次编码：根据目标大小和视频时长计算目标码率，然后一次编码完成。优点是快，缺点是文件大小可能有 10-20% 的偏差，因为视频内容复杂度不均匀，平均码率不能精确控制最终大小。"

"**Accurate** 是 two-pass 编码：第一次编码分析整个视频的内容复杂度，生成分析日志；第二次编码根据分析结果精确分配码率，复杂场景给更多码率，简单场景给更少。优点是文件大小偏差可以控制在 5% 以内，缺点是时间大约是 Fast 的两倍。"

"选择建议：如果对大小不太敏感，用 Fast；如果有严格限制（比如邮件附件 25MB），用 Accurate。"

---

### Q5：如何保证替换原文件不丢数据？

**回答：**

"我设计了 **backup-then-swap** 策略，流程是：

1. 压缩到临时文件（`.shrinkflow_tmp_{name}.mp4`）
2. 验证临时文件大小 > 0（防止空文件覆盖）
3. 将原文件重命名为备份文件
4. 将临时文件重命名为目标文件
5. 成功后删除备份文件
6. 任何步骤失败则回滚（恢复备份文件）"

"这个设计的关键是：**在任何时刻中断，都不会丢失数据**。

- 如果步骤 1-2 中断：原文件还在，临时文件可以忽略
- 如果步骤 3 中断：原文件已经重命名为备份，可以手动恢复
- 如果步骤 4 中断：备份还在，可以手动恢复
- 如果步骤 5 中断：新文件已经写入成功，备份可以忽略"

"还有一个技术细节：跨设备重命名（比如 C 盘文件移到 D 盘）会返回 EXDEV 错误，这时我会回退到 copyFile + unlink 策略。"

---

### Q6：为什么要内嵌 FFmpeg？

**回答：**

"三个原因：**零门槛**、**版本一致性**、**可靠性**。"

"**零门槛**：普通用户不知道什么是 FFmpeg，更不知道怎么安装和配置环境变量。内嵌后，下载安装就能用。"

"**版本一致性**：不同用户安装的 FFmpeg 版本可能不同，导致功能差异或行为不一致。内嵌后，所有用户使用相同版本。"

"**可靠性**：系统 PATH 中的 FFmpeg 可能被删除、移动或损坏。内嵌后，应用可以完全控制 FFmpeg 的生命周期。"

"为了平衡安装包大小和最新性，我设计了三优先级解析：用户更新版 > 内嵌版 > 系统 PATH（仅开发模式）。用户可以在应用内检查和更新 FFmpeg，更新使用原子目录切换，失败可回滚。"

---

### Q7：Electron 安全性如何考虑？

**回答：**

"Electron 应用的安全性主要关注三个层面："

"**第一，进程隔离**。我启用了 `contextIsolation`，禁用了 `nodeIntegration`。渲染进程（用户界面）不能直接访问 Node.js API，只能通过 `contextBridge` 暴露的受控 API 与主进程通信。这确保了即使渲染进程被 XSS 攻击，攻击者也无法直接访问文件系统或执行命令。"

"**第二，命令注入防护**。FFmpeg 命令使用参数数组传递，不拼接 shell 字符串。比如 `spawn('ffmpeg', ['-i', inputPath, ...args])` 而不是 `exec('ffmpeg -i ' + inputPath + ' ...')`。这防止了文件名中包含特殊字符时的命令注入风险。"

"**第三，文件操作安全**。FFmpeg 更新使用 Zip Slip 防护（校验解压路径），文件替换使用 backup-then-swap 策略，临时文件使用 `.shrinkflow_` 前缀方便识别和清理。"

---

### Q8：你做这个项目最大的难点是什么？

**回答：**

"最大的难点是**文件替换的安全性**。"

"用户选择'替换原文件'策略时，压缩后的文件需要覆盖原始文件。但如果压缩过程中断（断电、崩溃、磁盘满），原始文件就会丢失。这是一个不可逆的数据丢失风险。"

"我设计了 backup-then-swap 策略来解决这个问题，但实现过程中遇到了几个技术挑战：

1. **跨设备重命名** — C 盘文件移到 D 盘时，`rename` 会返回 EXDEV 错误，需要回退到 `copyFile + unlink`
2. **临时文件清理** — 应用异常退出后，临时文件需要在下次启动时清理
3. **回滚逻辑** — 每一步都需要考虑失败后的回滚，确保数据一致性"

"这个功能虽然看起来简单，但涉及到文件系统操作的原子性和一致性，是整个项目中最需要谨慎处理的部分。"

---

### Q9：如果继续迭代，你会优先做什么？

**回答：**

"我会优先做三件事：

**第一，应用自动更新**。当前用户需要手动下载新版本，体验不够好。我会集成 electron-updater，实现静默下载、用户确认后安装。

**第二，硬件编码器支持**。当前所有压缩模式都使用软件编码（libx264），速度较慢。我已经检测了用户的硬件编码器（NVENC、QSV、AMF），下一步是让用户选择使用硬件编码，大幅提升压缩速度。

**第三，macOS 打包支持**。当前只支持 Windows，但 Electron 天然支持跨平台，打包配置调整后可以快速支持 macOS。"

"这三个方向分别对应**用户体验**、**性能优化**和**用户覆盖**三个维度。"
