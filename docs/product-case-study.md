# ShrinkFlow 产品案例复盘

> AI 产品经理作品集 | 桌面工具类产品设计与工程落地

## 1. 项目背景

### 为什么做这个项目？

在日常工作中，我经常需要处理大量视频文件 — 课程录制、会议回放、素材归档。这些视频往往体积过大，上传到网盘、发送给同事、或者存储到移动硬盘时都会遇到问题。

市面上的视频压缩工具存在几个明显的断层：

- **在线工具** — 有文件大小限制，需要上传到云端，隐私无法保证
- **HandBrake** — 功能强大但界面复杂，普通用户难以理解 CRF、preset 等概念
- **命令行 FFmpeg** — 最灵活但门槛最高，参数组合需要深厚的专业知识
- **国产压缩工具** — 多数是 FFmpeg 的简单 GUI 封装，缺乏批量工作流和安全保护

我想要的其实很简单：**选一堆视频，点一下，告诉我大概要多久，压缩完告诉我节省了多少空间。** 但现有工具都没有很好地满足这个需求。

### 项目定位

ShrinkFlow 不是要做一个"更好的 HandBrake"，而是要做一个**"普通人也能用的批量视频压缩工作流工具"**。

核心设计原则：
1. **零门槛** — 用户不需要知道什么是 FFmpeg、CRF、preset
2. **批量优先** — 单文件压缩是特殊情况，批量才是常态
3. **可控可解释** — 告诉用户压缩要多久、为什么这么慢、结果如何
4. **数据安全** — 绝不能因为压缩操作丢失原始文件

## 2. 用户痛点

### 痛点矩阵

| 痛点 | 严重程度 | 现有方案 | ShrinkFlow 方案 |
|---|---|---|---|
| 视频太大，上传/分享困难 | 高 | 手动用 FFmpeg 命令 | 一键压缩，6 种模式可选 |
| 批量处理多个视频 | 高 | 逐个处理或写脚本 | 文件夹递归扫描 + 串行队列 |
| 不知道压缩要多久 | 中 | 凭经验猜测 | 三层 ETA 预估系统 |

| FFmpeg 安装配置麻烦 | 中 | 自行下载配置 | 内嵌 FFmpeg，应用内更新 |
| 压缩结果无法追踪 | 中 | 无 | 历史记录 + JSON/CSV 导出 |

### 用户画像

**主要用户：** 需要批量压缩视频的个人用户

- 内容创作者 — 素材库需要定期清理，压缩存储空间
- 普通用户 — 手机拍的视频太大，想压缩后分享给朋友
- IT 从业者 — 需要处理大量会议录像

**典型场景：**
- "我有 50 个课程视频，每个 2GB，想压缩到 500MB 左右上传到网盘"
- "我拍了一堆手机视频，想压缩后存到移动硬盘里"
- "我想把 MKV 格式的视频转成 MP4，同时压缩一下大小"

## 3. 产品目标

### 核心目标

**让用户用最少的操作完成批量视频压缩，并且清楚地知道结果。**

### 可衡量指标

| 指标 | 目标 | 当前状态 |
|---|---|---|
| 批量压缩完成率 | >95% | 已实现（失败继续机制） |

- 不做实时预览（压缩前预览效果）
- 不做多格式输出（统一输出 H.264 MP4）

## 4. 核心用户流程

### 主流程

```
添加视频 → 选择压缩模式 → 开始压缩 → 查看结果 → 导出记录
    │           │              │           │           │
    │           │              │           │           └── JSON/CSV
    │           │              │           └── 压缩率、耗时、节省空间
    │           │              └── 实时进度、ETA、可取消
    │           └── 6 种模式 + 目标大小设置
    └── 拖拽/文件选择/文件夹扫描
```

### 关键决策点

1. **添加视频后** — 自动分析元信息，展示时长、分辨率、编码、码率
2. **选择模式时** — 每种模式有清晰的说明和适用场景
3. **目标大小模式** — 校验目标大小合理性，防止过度压缩
4. **压缩开始前** — 检测同名冲突，提供覆盖/重命名/跳过选项
5. **压缩过程中** — 实时进度、可取消、单文件失败不影响队列
6. **压缩完成后** — 汇总结果、自动打开输出文件夹（可选）

## 5. 关键功能设计

### 5.1 从"能压缩"到"批量压缩工作流"

**设计决策：** 单文件压缩是特殊情况，批量才是常态。

- 文件夹递归扫描 — 一键导入整个视频目录
- 自动去重 — 按文件路径去重，避免重复处理
- 智能跳过 — 自动跳过输出目录、node_modules 等非视频目录
- 扫描进度 — 大目录扫描时显示实时进度（节流：300ms 或 100 个文件）

**技术实现：** `file-scanner` 模块支持 `recursive` 选项，通过 `realpath` 追踪检测符号链接循环，`SKIP_DIRECTORY_NAMES` 集合自动跳过已知输出目录。

### 5.2 从"能压缩"到"安全、可控、可解释"

**设计决策：** 用户信任来自透明和可控。

- **压缩前** — 展示视频元信息、预估压缩结果、预估耗时
- **压缩中** — 实时百分比、速度（x 倍速）、ETA
- **压缩后** — 原始大小、压缩后大小、节省百分比、实际耗时
- **任何时候** — 可以取消，取消后已完成的文件保留

### 5.3 为什么需要 Target Size Fast 和 Accurate

**场景驱动：** 用户最常见的需求是"我想把这个视频压缩到 100MB 以内"。

- **Target Size Fast** — 单次编码，速度较快，但文件大小可能有 10-20% 偏差
- **Target Size Accurate** — Two-pass 编码，第一次分析内容复杂度，第二次精确分配码率，文件大小偏差 <5%

**设计权衡：** Fast 模式牺牲精度换取速度，适合对大小不太敏感的场景；Accurate 模式牺牲时间换取精度，适合有严格大小限制的场景（如邮件附件、平台上传限制）。

**技术细节：**
- 两种模式都使用 MiB（1024*1024）计算，避免单位混淆
- 最低视频码率校验：100kbps 硬错误，500kbps 警告
- Accurate 模式预留 5% 容器开销，防止实际文件超出目标
- Two-pass 日志写入系统临时目录，完成后自动清理

### 5.4 为什么需要 FFmpeg 内嵌和检查更新

**问题：** 用户手动安装 FFmpeg 的门槛太高。

- Windows 用户需要下载、解压、配置环境变量
- 版本不一致可能导致功能差异
- 普通用户不知道什么是 PATH

**解决方案：**
- 应用内嵌 FFmpeg 二进制文件，开箱即用
- 提供应用内更新功能，用户无需离开应用
- 三优先级解析：用户更新版 > 内嵌版 > 系统 PATH（仅开发模式）
- 更新使用原子目录切换，失败可回滚

**技术实现：**
- `ffmpeg-manager` 模块管理 FFmpeg 二进制的完整生命周期
- 从 GitHub BtbN/FFmpeg-Builds 获取最新构建
- SHA-256 校验确保下载完整性
- Zip Slip 防护确保解压安全
- `metadata.json` 记录已安装版本，避免重复下载
- 启动时自动修复中断的更新状态

### 5.5 为什么替换原文件要做 backup-then-swap

**场景：** 用户选择"替换原文件"策略时，压缩后的文件需要覆盖原始文件。

**风险：** 如果直接覆盖，压缩过程中断（断电、崩溃）会导致原始文件丢失。

**解决方案：backup-then-swap**
1. 压缩到临时文件（`.shrinkflow_tmp_{name}.mp4`）
2. 验证临时文件大小 > 0
3. 将原文件重命名为备份文件
4. 将临时文件重命名为目标文件
5. 成功后删除备份文件
6. 任何步骤失败则回滚（恢复备份文件）

**技术细节：**
- 跨设备重命名（EXDEV 错误）时回退到 `copyFile + unlink`
- 每一步都有错误处理和回滚逻辑
- 临时文件使用 `.shrinkflow_tmp_` 前缀，方便识别和清理

### 5.6 为什么要做历史记录和导出

**用户需求：**
- "我压缩了这么多文件，总共节省了多少空间？"
- "上次压缩那个文件用了多久？"
- "我想记录一下压缩结果，方便以后对比"

**设计决策：**
- 每次压缩任务自动记录到历史
- 支持查看单个文件的详细结果
- 支持导出为 JSON（结构化数据）和 CSV（方便 Excel 打开）
- 最多保存 100 条 benchmark 记录，用于 ETA 预估

## 6. 技术架构设计

### 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│                    Renderer (React SPA)                      │
│  React 18 + React Router 6 + Zustand + Tailwind CSS + i18next│
└──────────────────────────┬──────────────────────────────────┘
                           │ contextBridge (window.api)
┌──────────────────────────▼──────────────────────────────────┐
│                    Preload (IPC Bridge)                      │
│  受控 API 暴露，事件监听返回 unsubscribe 函数                  │
└──────────────────────────┬──────────────────────────────────┘
                           │ ipcMain.handle / ipcMain.on
┌──────────────────────────▼──────────────────────────────────┐
│                    Main Process (Node.js)                    │
│  FileScanner / VideoAnalyzer / CompressionPlanner            │
│  FFmpegRunner / TaskQueue / OutputManager                    │
│  FFmpegManager / HistoryStore / EtaEstimator                 │
│  SettingsStore / BenchmarkStore / DeviceProfiler             │
└──────────────────────────┬──────────────────────────────────┘
                           │ spawn / execFile (参数数组)
┌──────────────────────────▼──────────────────────────────────┐
│                    FFmpeg / FFprobe                          │
└─────────────────────────────────────────────────────────────┘
```

### 模块职责

| 模块 | 职责 | 关键设计 |
|---|---|---|
| FileScanner | 递归扫描视频文件 | 符号链接循环检测、目录跳过、去重、进度节流 |
| VideoAnalyzer | FFprobe 元信息提取 | 并发控制（最多 2 个）、损坏文件检测 |
| CompressionPlanner | 生成 FFmpeg 命令参数 | 6 种模式、two-pass 支持、码率校验 |
| FFmpegRunner | 执行 FFmpeg 进程 | 进度解析、取消支持、two-pass 阶段管理 |
| TaskQueue | 串行批量队列 | EventEmitter 事件驱动、失败继续、状态管理 |
| OutputManager | 输出路径和冲突处理 | 三种策略、冲突检测、backup-then-swap |
| FFmpegManager | FFmpeg 二进制管理 | 三优先级解析、应用内更新、启动修复 |
| EtaEstimator | ETA 预估 | 三层数据源、置信度评估 |
| HistoryStore | 历史记录持久化 | JSON 存储、JSON/CSV 导出 |
| BenchmarkStore | 压缩速度基准 | 最多 100 条、按分辨率/模式查询 |
| DeviceProfiler | 硬件信息检测 | CPU/内存/硬件编码器发现 |
| SettingsStore | 设置持久化 | JSON 存储、Schema 迁移 |

### IPC 通信设计

- **`ipcMain.handle`** — 请求-响应模式，用于数据查询和操作（27 个）
- **`ipcMain.on`** — 单向通知，用于取消、打开文件夹等（5 个）
- **事件推送** — 主进程主动推送进度到渲染进程（7 个事件类型）
- **Unsubscribe 模式** — 事件监听返回取消订阅函数，防止内存泄漏

### 状态管理设计

使用 Zustand 单一 Store，管理视频文件的完整生命周期：

```
scanned → analyzing → ready → pending → compressing → completed/failed/canceled/skipped
```

关键保护机制：
- **队列级终端状态守卫** — 队列完成后不再接受进度更新
- **单文件终端状态守卫** — 文件完成后不再接受进度更新
- **状态回归守卫** — 队列状态不能从终端状态回退到非终端状态
- **最终对账** — 队列结束后强制修正卡在 compressing 状态的文件

## 7. 重要取舍

### 取舍 1：串行 vs 并行压缩

**决策：** 串行压缩（一次只压缩一个文件）

**理由：**
- FFmpeg 压缩是 CPU 密集型操作，并行会导致系统卡顿
- 串行更容易追踪进度和处理失败
- 用户通常不需要同时压缩多个文件，而是等待批量完成

**代价：** 批量压缩总时间更长

### 取舍 2：H.264 only vs 多编码器支持

**决策：** 统一使用 H.264 (libx264) + AAC

**理由：**
- H.264 兼容性最好，几乎所有设备和平台都支持
- 简化用户选择，降低决策成本
- 后续可以通过硬件编码器扩展

**代价：** 无法利用 H.265/AV1 等更高效率的编码器

### 取舍 3：Electron vs 原生应用

**决策：** 使用 Electron 构建跨平台桌面应用

**理由：**
- Web 技术栈开发效率高
- React 生态丰富，UI 开发快
- 后续可以相对容易地扩展到 macOS/Linux

**代价：** 安装包体积较大（~150MB，含 FFmpeg）

### 取舍 4：内嵌 FFmpeg vs 依赖系统安装

**决策：** 内嵌 FFmpeg 二进制文件

**理由：**
- 零门槛，用户无需手动安装
- 版本一致性有保证
- 避免系统 PATH 配置问题

**代价：** 安装包体积增加约 100MB

### 取舍 5：JSON 文件存储 vs SQLite

**决策：** 使用 JSON 文件存储设置、历史、基准数据

**理由：**
- 实现简单，无需额外依赖
- 数据量小（个人工具），性能足够
- 方便调试和手动编辑

**代价：** 不适合大规模数据，并发写入需要小心

## 8. 遇到的问题和解决方案

### 问题 1：FFmpeg 进度解析

**问题描述：** FFmpeg 的 `-progress` 输出格式不规范，不同版本可能有差异。

**解决方案：**
- 使用 `-progress pipe:1 -nostats` 参数，确保输出到 stdout
- 按行解析 key=value 格式，处理 `out_time_us` 计算百分比
- 优雅降级：解析失败时不崩溃，只是不显示进度

### 问题 2：Two-pass 编码的进度追踪

**问题描述：** Two-pass 编码有两个阶段，如何给用户展示统一的进度？

**解决方案：**
- Pass 1 映射到 0-50%，Pass 2 映射到 50-100%
- 每个阶段独立解析 FFmpeg 进度
- Pass 日志写入系统临时目录，完成后自动清理

### 问题 3：文件替换时的数据安全

**问题描述：** 替换原文件时，如果压缩过程中断，原始文件会丢失。

**解决方案：** backup-then-swap 策略
1. 压缩到临时文件
2. 验证临时文件完整性
3. 备份原文件
4. 替换
5. 成功删除备份，失败回滚

### 问题 4：大目录扫描性能

**问题描述：** 扫描包含数千个文件的目录时，UI 会卡顿。

**解决方案：**
- 异步扫描，不阻塞主线程
- 进度事件节流（300ms 或 100 个文件）
- 跳过已知非视频目录（node_modules、dist 等）
- 符号链接循环检测（realpath 追踪）

### 问题 5：FFmpeg 更新的原子性

**问题描述：** FFmpeg 更新过程中如果应用崩溃，可能导致二进制文件损坏。

**解决方案：**
- 使用 staging → current → previous 目录切换
- 写入 `metadata.json` 记录版本信息
- 启动时自动检测并修复中断的更新
- 更新期间阻止新的压缩任务

### 问题 6：Electron 安全性

**问题描述：** Electron 应用的安全性一直是业界关注点。

**解决方案：**
- 启用 `contextIsolation`，禁用 `nodeIntegration`
- 通过 `contextBridge` 暴露最小化 API
- 使用参数数组传递 FFmpeg 命令，不拼接 shell 字符串
- ASAR 解包 FFmpeg 资源，确保可执行权限

## 11. 面试讲解要点

### 开场（30 秒）

"ShrinkFlow 是一个基于 Electron + FFmpeg 的桌面端批量视频压缩工具。它的核心价值是让普通用户也能轻松完成批量视频压缩，不需要了解 FFmpeg 的复杂参数。"

### 产品设计亮点（1 分钟）

"在产品设计上，我重点关注了三个维度：

1. **批量工作流** — 不是简单的单文件压缩，而是从文件夹扫描、去重、队列管理到结果追踪的完整工作流
2. **安全可控** — backup-then-swap 机制确保替换原文件时不会丢失数据，三层 ETA 预估让用户清楚知道要等多久
3. **零门槛** — 内嵌 FFmpeg，用户不需要手动安装任何依赖"

### 技术实现亮点（1 分钟）

"在技术实现上，有几个关键设计：

1. **Electron 安全桥接** — contextIsolation 启用，通过 contextBridge 暴露最小化 API
2. **Two-pass 精确压缩** — Target Size Accurate 模式通过两次编码精确控制输出大小
3. **原子更新** — FFmpeg 更新使用 staging/current/previous 目录切换，失败可回滚
4. **事件驱动架构** — TaskQueue 基于 EventEmitter，支持实时进度推送和取消"

### 遇到的挑战（30 秒）

"最大的挑战是文件替换的安全性。用户选择替换原文件时，如果压缩过程中断，原始文件会丢失。我设计了 backup-then-swap 策略：先压缩到临时文件，验证完整性后备份原文件，替换成功后删除备份，失败则自动回滚。"

### 项目价值（30 秒）

"这个项目展示了我作为 AI 产品经理的能力：

1. **需求分析** — 从真实痛点出发，不是为了技术而技术
2. **产品设计** — 关注用户体验的每个细节
3. **工程落地** — 从 Demo 到可打包版本的完整推进
4. **安全意识** — 数据安全和应用安全的双重保障"
