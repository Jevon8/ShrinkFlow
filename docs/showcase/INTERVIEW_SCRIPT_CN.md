# ShrinkFlow v1.2.0 — 面试讲解稿

## 一、1 分钟精简版

> "ShrinkFlow 是一款元数据感知的视频批量压缩工具。核心创新是一个 6 层规则引擎：它分析每个视频的编码格式、码率、分辨率，为每个文件独立推荐压缩策略——压缩、跳过、还是需要用户确认。用户只需选择目标强度（轻度/中度/重度），系统完成剩下的决策。所有决策可解释，附带 17 种 reason code。有四重安全保护，包括输出变大保护和原子替换。FFmpeg 内嵌，完全离线。当前 v1.2.0 已完成 Windows 安装包，约 167MB。"

---

## 二、3 分钟标准版

### 背景与痛点（45 秒）

"视频压缩工具有三个普遍问题。第一，一刀切——所有视频用同一参数，不管它已经是 HEVC 还是 ProRes。第二，不安全——压完直接覆盖原文件，输出变大了也不知道。第三，门槛高——FFmpeg 参数复杂，普通用户不会用。"

### 产品方案（45 秒）

"ShrinkFlow 的解决方案是：让系统做决策，而不是让用户做决策。我设计了一个 6 层规则引擎——第一层硬排除（元数据损坏、文件太小、时长太短），第二层编码分类（高效/通用/编辑/未知四类），第三层证据收集（BPPF 五档分级），第四层目标决策（根据用户选的轻度/中度/重度做 compress/skip/confirm），第五层高风险降级（高效编码重压缩自动降级为确认），第六层低收益过滤。每个决策附带 reason code，用户能看到'为什么'。"

### 技术亮点（45 秒）

"技术栈是 Electron + React + TypeScript + FFmpeg。主进程 36 个 IPC handler，渲染进程的规则引擎是纯 TypeScript 模块，可独立测试。压缩队列是 EventEmitter 驱动的串行队列，支持双 Pass 编码和取消。文件操作用备份-替换原子策略，失败自动回滚。FFmpeg 三源解析：内嵌 > 已更新 > 系统 PATH。"

### 成果与规划（45 秒）

"v1.2.0 已完成：167MB Windows 安装包，FFmpeg 内嵌，零外部依赖。7 种压缩模式，3 级智能策略，17 种 reason code，4 重安全保护。v0.3 规划三个方向：Smart Probe（5 秒快速试压提升估算精度）、历史反馈学习（用过去结果修正未来估算）、SSIM/PSNR 质量评估。"

## 三、5 分钟完整版

### 第一部分：项目背景（1 分钟）

"ShrinkFlow 是我在 2026 年独立完成的桌面端产品，从需求定义到架构设计到代码实现到打包发布，全程独立完成。

我发现一个普遍问题：视频创作者、内容运营、普通用户都有批量压缩视频的需求——释放磁盘空间、准备上传素材、归档旧视频。但现有工具有三个缺陷：

第一，一刀切。所有视频用同一个 CRF 值，不管这个视频是已经压过的 HEVC 还是码率超高的 ProRes。
第二，不安全。压完直接覆盖原文件，输出变大了也不知道，画质崩了无法恢复。
第三，门槛高。FFmpeg 命令行参数复杂，普通用户不会用；在线工具需要上传隐私视频。"

### 第二部分：产品判断（1 分钟）

"我的核心判断是：视频压缩不应该是用户做决策，应该是系统做决策。用户只需要表达意图——'我要省空间'或'我要保画质'——系统根据每个视频的实际特征，独立决定该压、该跳过、还是该让用户确认。

这个判断背后的产品逻辑是：压缩参数（CRF、preset、编码格式）是手段，不是目的。用户关心的是'省多少空间'和'画质会不会变差'，不是'CRF 应该设 21 还是 25'。所以我要做的不是给用户更多参数选择，而是替用户做参数决策，同时让决策过程可解释、可覆盖。"

### 第三部分：技术实现（1.5 分钟）

"核心是一个 6 层规则引擎。

第一层，硬排除——元数据损坏、文件小于 20MB、时长小于 5 秒的直接跳过。
第二层，编码分类——把所有编码格式分成 4 类：高效编码（HEVC/AV1/VP9）重压缩有画质风险、通用编码（H.264）最安全、编辑编码（ProRes/DNxHD）压缩空间大但需注意、未知编码保守处理。
第三层，证据收集——计算 BPPF（每帧每像素比特数），分 5 档。结合分辨率、文件大小收集 reason code。
第四层，目标决策——根据用户选择的策略做 compress/skip/confirm 决策。比如轻度策略下，高效编码一律确认、低 BPPF 跳过；重度策略下，大部分视频直接压缩。
第五层，高风险降级——如果质量风险评估为 high，自动降级为 confirm。
第六层，低收益过滤——预估节省不到阈值的自动跳过。阈值随目标变化：轻度 15%，重度 3%。

所有决策附带 17 种 reason code，用户能看到'为什么这个视频被跳过'。"

### 第四部分：迭代过程（30 秒）

"v0.1.0 是基础版。v1.2.0 加入规则引擎和 per-video mode。

迭代中有一个关键问题：Smart Plan 的统计数据和视频列表筛选用了不同数据源——summary 来自 useMemo，视频建议来自 Zustand store，切换目标后不同步。通过统一为 adviceByVideoId Map 作为 single source of truth 解决。这个经历让我理解了在复杂状态管理中，数据源一致性比功能实现更重要。"

### 第五部分：成果与规划（30 秒）

"v1.2.0 已完成：167MB Windows 安装包，FFmpeg 内嵌，零外部依赖。7 种压缩模式，3 级智能策略，17 种 reason code，4 重安全保护，中英双语。

v0.3 规划：Smart Probe（5 秒试压提升精度）、历史反馈学习、SSIM/PSNR 质量评估、专业报告页、用户预设系统。"

## 四、面试官追问与回答

### Q1：这个项目 AI 在哪里？

**回答：** "当前 v1.2.0 的核心是元数据感知的可解释规则引擎，不是机器学习模型。规则引擎基于编码学原理设计：BPPF（每帧每像素比特数）衡量压缩程度，编码格式分类判断重压缩风险，目标乘数调整策略偏好。所有决策可解释——17 种 reason code 让用户理解'为什么'。

v0.3 规划引入两个数据驱动的增强：Smart Probe（5 秒快速试压获取实际编码速度，替代规则估算）和历史反馈学习（用过去压缩结果修正未来估算）。这些是从规则驱动向数据驱动的演进路径。"

### Q2：为什么不用纯 FFmpeg GUI？

**回答：** "FFmpeg GUI 解决的是'怎么压缩'的问题——给用户更多参数面板。ShrinkFlow 解决的是'该不该压缩'和'用什么参数压缩'的问题。一个用户有 100 个视频，FFmpeg GUI 需要用户逐个判断每个视频该设什么 CRF。ShrinkFlow 一次性分析所有文件，输出一个计划：72 个压缩、20 个跳过、8 个需确认。用户点一下就能执行。"

### Q3：Smart Shrink Plan 怎么判断？

**回答：** "核心指标是 BPPF（bits-per-pixel-per-frame）= bitrate / (width × height × fps)。它衡量每个像素每帧用了多少比特，是国际通用的视频压缩效率指标。

引擎分 5 档：≤0.045 是 already_compressed（已经压得很狠），0.045-0.075 是 low，0.075-0.12 是 medium，0.12-0.20 是 high，>0.20 是 very_high。

结合编码格式分类——高效编码（HEVC/AV1）重压缩有画质风险所以保守处理，通用编码（H.264）安全所以积极处理，编辑编码（ProRes）压缩空间大但需确认——形成 per-video 决策。"

### Q4：如何避免压缩后变大？

**回答：** "四重保护机制：

1. 输出变大保护：压缩后 stat 比较输入输出文件大小，如果 output ≥ input，自动跳过替换，保留原始文件。这是在 task-queue 的后处理阶段实现的。
2. 低收益过滤：预估节省不到阈值的视频直接跳过，不会浪费时间压缩一个几乎不会变小的文件。
3. 高风险确认：高效编码（HEVC/AV1）重压缩可能反而变大（因为 H.264 编码效率低于 HEVC），自动降级为 confirm，强制用户确认。
4. 原子替换：即使在替换过程中出错，备份-替换策略保证可以回滚到原始文件。"

### Q5：为什么需要 per-video mode？

**回答：** "一个批次里的视频通常来源多样：手机录的 H.264、相机拍的 ProRes、别人发来的 HEVC、老素材是 MPEG-2。这些视频的压缩特征完全不同：

- H.264 高码率视频：用 CRF 21 压缩，可能省 40-60%
- HEVC 低码率视频：已经是高效编码 + 低 BPPF，压了也不会小多少，应该跳过
- ProRes 素材：压缩空间大（50-85%），但用太狠参数可能画质崩，需要确认
- 某些视频：压缩后反而变大（HEVC→H.264 转码），必须跳过

如果用同一个模式，要么太保守（省不了多少空间），要么太激进（损坏画质）。per-video mode 让每个文件用自己的最优解。"

### Q6：v0.3 会怎么做？

**回答：** "三个方向：

1. **Smart Probe**：压缩前用 FFmpeg 截取视频中间 5 秒，用目标模式快速压缩，测量实际编码速度和输出/输入大小比。这比纯规则估算更准确。
2. **历史反馈学习**：按 (codecClass, bppfTier, mode) 分桶存储历史压缩比，`estimateSaving()` 查询分桶数据替代固定范围。用得越久估算越准。
3. **质量评估**：压缩后用 SSIM/PSNR 量化画质变化。用户看到'SSIM 0.98'就知道画质几乎没损失，比'可能有轻微画质损失'更有说服力。"

### Q7：你在这个项目里体现了哪些产品能力？

**回答：**

"1. **把决策系统融入用户流程**——不是做一个独立的分析工具，而是把规则引擎嵌入到批量压缩的流程中。用户感知不到引擎的存在，但每个决策都是引擎驱动的。

2. **平衡自动化和可控性**——全自动会失去用户信任，全手动太累。我设计了'自动决策 + 透明展示 + 随时覆盖'的交互模式。

3. **可解释性优先**——17 种 reason code 让每个决策透明。这不是黑盒，用户能理解'为什么'，才能信任'建议'。

4. **安全优先的产品设计**——四重保护机制确保'不损坏'是第一优先级。输出变大保护、原子替换、高风险确认、低收益过滤。

5. **复杂状态协同**——Smart Plan、队列进度、筛选逻辑、历史记录、压缩配置通过 Zustand + sessionId 机制保证一致性。"
