# ShrinkFlow v0.3 路线图

## 概述

v1.2.0 建立了可解释规则引擎和 per-video 压缩决策的基础。v0.3 的方向是从纯规则驱动向数据驱动演进——用实际压缩结果和快速试压数据提升估算精度，同时增加质量维度的可见性。

---

## 方向 1：Smart Probe 智能试压

### 做什么
压缩前用 FFmpeg 截取视频中间 5 秒片段，用目标模式快速压缩，测量实际编码速度（fps）和输出/输入大小比。

### 解决什么问题
当前 ETA 和节省估算基于规则（像素复杂度 + 编码分类 + BPPF 分层 + 目标乘数）。这些规则是静态的，不考虑具体视频内容的复杂度（如运动剧烈程度、噪点多少）。同一个 BPPF 档的视频，实际压缩比可能差异很大。

### 技术方案
1. 用 FFmpeg 截取视频中间 5 秒（`-ss MIDDLE -t 5`）
2. 用目标压缩模式压缩这个片段
3. 测量：实际编码速度（fps）、输出大小 / 输入大小比
4. 将结果用于修正 `estimateSaving()` 的 min/max 范围
5. 试压文件放在 `os.tmpdir()`，用完清理

### 用户价值
- 更准确的节省预估范围（从"30-60%"缩小到"42-51%"）
- 更准确的 ETA（基于实际编码速度而非规则估算）
- 用户在压缩前就能看到更可靠的预期结果

### 风险点
- 5 秒片段可能不代表整个视频的特征（如 VBR 视频不同段落码率差异大）
- 试压本身需要时间（每个视频 3-8 秒），大批量时累积不可忽略
- 需要决定试压时机：导入时全部试压 vs 用户请求时试压 vs 后台异步试压

### MVP 范围
- 对用户选中的视频（非全部）执行试压
- 试压结果用于修正节省估算的 min/max
- 试压进度单独显示，不阻塞主流程
- 只对 ready 状态的视频执行

### 不做什么
- 不做全量帧对比（太慢）
- 不做试压结果持久化（每次重新计算）
- 不做自动试压（用户主动触发）

## 方向 2：历史反馈学习

### 做什么
用历史压缩结果修正未来的节省估算。按 (codecClass, bppfTier, mode) 分桶存储实际压缩比，`estimateSaving()` 查询分桶数据替代或修正固定范围。

### 解决什么问题
当前 `estimateSaving()` 使用固定的 base range（如 common + high bppf = 30-60%）。这个范围是基于编码学原理的通用估算，不考虑用户实际视频内容的特征。用户用得越多，积累的实际数据越能反映其视频库的真实压缩特征。

### 技术方案
1. 历史记录中已有 inputSize、outputSize、mode
2. 从视频元数据中提取 codecClass 和 bppfTier（可能需要在历史记录中新增这两个字段）
3. 按 (codecClass, bppfTier, mode) 分桶，存储最近 N 条记录的实际压缩比
4. `estimateSaving()` 优先查询分桶数据：如果有 ≥3 条记录，用分桶的 P25/P75 替代固定范围
5. 分桶数据不足时回退到规则估算

### 用户价值
- 用得越久，估算越准
- 对用户特定视频库的特征有更好适配（如用户主要处理手机视频 vs 专业素材）

### 风险点
- 历史数据可能有偏差（如用户只压缩高码率视频，分桶数据不代表低码率视频）
- 分桶粒度需要调优：太粗（如只按 codecClass）不够精确，太细（如按具体分辨率）数据不足
- 历史数据可能过时（如用户换了拍摄设备）

### MVP 范围
- 在 history-store 中新增 codecClass、bppfTier 字段
- 按 (codecClass, bppfTier) 二级分桶（暂不按 mode 分）
- ≥3 条记录时用分桶数据，否则回退规则
- 分桶数据上限 100 条/桶，FIFO 淘汰

### 不做什么
- 不做跨用户数据共享（隐私考虑）
- 不做自动模型训练
- 不做复杂的异常检测（如过滤异常压缩比）

## 方向 3：压缩质量评估（SSIM / PSNR）

### 做什么
压缩后用 SSIM / PSNR 量化画质变化，让用户看到具体的画质损失数字。

### 解决什么问题
当前只有"输出变大保护"（体积维度），没有"画质损失量化"（质量维度）。用户不知道"压了 40% 空间"对应"画质损失了多少"。"可能有轻微画质损失"这种描述太模糊。

### 技术方案
1. FFmpeg 内置 `ssim` 和 `psnr` 滤镜，可以对比原始和压缩后的视频
2. 取样关键帧（首帧、1/4 处、中间、3/4 处、尾帧）降低计算量，避免全帧对比的性能开销
3. 输出 SSIM 均值（0-1，越高越好）和 PSNR 均值（dB，越高越好）
4. 存储在历史记录中

### 用户价值
- "SSIM 0.98"比"可能有轻微画质损失"更有说服力
- 用户可以基于具体数字做决策：SSIM > 0.95 可以放心压缩，SSIM < 0.90 需要谨慎
- 历史记录中可以对比不同模式的质量表现

### 风险点
- SSIM/PSNR 计算需要解码原始和压缩后的视频，性能开销较大
- 全帧对比太慢，取样帧可能不具代表性
- SSIM/PSNR 是全参考指标，需要原始文件存在——如果用户选择了"替换原始"模式，原始文件已被替换

### MVP 范围
- 只在"默认保存"模式下执行（原始文件保留）
- 取样 5 个关键帧计算 SSIM/PSNR 均值
- 结果显示在历史记录详情中
- 不阻塞压缩流程，后台异步计算

### 不做什么
- 不做 VMAF（需要额外依赖）
- 不做实时质量预览
- 不做全帧对比（性能不可接受）

## 方向 4：专业报告页

### 做什么
批量压缩完成后的汇总报告页，展示整体压缩成果。

### 解决什么问题
当前结果分散在进度面板和历史记录中。用户完成一个批次的压缩后，没有一个统一的视角来回顾：总共省了多少空间、哪些视频压缩效果最好、用了哪些模式、质量表现如何。

### 技术方案
1. 新增 `ReportPage` 路由
2. 数据来源：当次压缩结果（queueResult）+ 历史记录
3. 展示内容：
   - 总节省空间（字节 + 百分比）
   - 平均压缩比
   - 模式分布饼图（每个模式处理了多少视频）
   - Top 5 最省空间的视频
   - Top 5 压缩比最高的视频
   - 质量评估分布（如有 SSIM 数据）
4. 支持导出为 JSON / CSV

### 用户价值
- 一目了然的压缩成果展示
- 适合分享和汇报（如"这批视频省了 5GB"）
- 帮助用户评估不同策略的效果

### 风险点
- 需要设计数据展示的 UI 布局
- 图表实现可能需要额外依赖（或用 CSS 实现简单图表）

### MVP 范围
- 纯文本 + 简单数字展示（不做复杂图表）
- 展示当次压缩结果
- 支持导出 JSON

### 不做什么
- 不做复杂图表库集成
- 不做跨批次对比
- 不做 PDF 导出

## 方向 5：用户预设系统

### 做什么
用户自定义压缩预设（保存 / 加载 / 分享）。

### 解决什么问题
当前 7 种模式是固定的。高级用户可能想要自定义参数组合，如"CRF 23 + slow + yuv420p + AAC 192k"。他们需要保存这些组合以便复用。

### 技术方案
1. 预设数据结构：{ name, crf, preset, pixFmt, audioBitrate, description }
2. 持久化：JSON 文件存储在 userData 目录
3. UI：预设管理器（列表 + 新增 / 编辑 / 删除 / 导入 / 导出）
4. 与 CompressionModeCards 集成：新增"自定义"卡片，点击后展开预设列表

### 用户价值
- 高级用户创建"我的最佳预设"
- 一键复用，不需要每次手动调参数
- 可以分享预设给同事

### 风险点
- 自定义参数可能导致 FFmpeg 执行失败（如不支持的 CRF 值）
- 需要参数校验

### MVP 范围
- 预设 CRUD（新增 / 编辑 / 删除）
- 持久化到 userData
- 集成到 CompressionModeCards
- 基本参数校验（CRF 0-51, preset 白名单）

### 不做什么
- 不做预设分享（需要后端服务）
- 不做预设导入/导出（MVP 暂不做）
- 不做预设模板（如"适合 YouTube 的预设"）

## 优先级排序

| 优先级 | 方向 | 理由 |
|--------|------|------|
| P0 | Smart Probe | 直接提升核心体验（估算精度），技术实现相对独立 |
| P1 | 历史反馈学习 | 与 Smart Probe 互补，数据积累需要时间，尽早开始 |
| P2 | 质量评估 | 用户价值高，但实现复杂度也高 |
| P3 | 报告页 | 锦上添花，不影响核心流程 |
| P4 | 用户预设 | 面向高级用户，优先级较低 |

## 技术依赖关系

```
Smart Probe ──→ 修正 estimateSaving()
                    │
                    ├──→ 更准确的 Smart Shrink Plan
                    │
历史反馈学习 ──→ 修正 estimateSaving()
                    │
                    └──→ 更准确的 Smart Shrink Plan

质量评估 ──→ history-store 新增 quality 字段
                    │
                    └──→ 报告页展示质量分布

用户预设 ──→ 独立，无强依赖
```

Smart Probe 和历史反馈学习都作用于 `estimateSaving()`，可以分阶段实现，最终合并。质量评估和报告页有数据依赖关系。用户预设相对独立。
